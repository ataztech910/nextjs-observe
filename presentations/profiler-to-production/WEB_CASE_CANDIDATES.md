# Выбор основного веб-расследования

## Текущий кандидат — layout за пределами React render duration

[Диагностический пример и результаты](web-case/LAYOUT_INSPECTION.md): подгонка ширины 120 карточек.
При render actualDuration 4.2/4.5 ms, внутри layout effect наблюдаются 120 против 1 Layout events.
В полном записанном окне после handler — 121 против 2, итоговые карточки совпадают.
19 ноября выполнены [шесть запланированных пар](web-case/LAYOUT_COMPARISON.md) без tracing:
Event Timing interaction maximum меньше во всех шести, медианы 88 → 64 ms; итог всех 120 карточек совпал.
0 missing/invalid, включая сохранённую пару 176/64 ms. Это локальное directional observation,
не полевой INP, physical presentation или population claim. Учебный DOM-пример остаётся учебным,
диагностические traces и повторные timings получены отдельно. График и текст уже добавлены в deck.
Mismatch ниже сохраняем коротким объяснением, не продолжаем исследовать его цену без нового основания.

18 ноября 2026. Маленький шаг после теоретической сцены «Visible ≠ interactive»:
просмотр исходников, без нового приложения, профилирования или исправления.

## Кандидат: сервер отдал HTML, но клиент получил другое содержимое

В существующем учебном приложении `workshop-ai-observability/app/product/[id]/viewers.tsx`
найден клиентский React-компонент:

```tsx
export function Viewers() {
  const viewers = 2 + Math.floor(Math.random() * 30)
  return <p className="muted">{viewers} people are looking at this right now</p>
}
```

Он включён в Next.js product page рядом с ценой. Входное значение не передаётся с сервера;
компонент вычисляет случайное число при каждом render. Серверный и клиентский render могут дать разный текст;
случайное совпадение тоже возможно. Это конкретный источник недетерминированного содержимого,
а не специально добавленный тяжёлый цикл.

**Рабочий вопрос:** приводит ли расхождение к hydration recovery на установленной версии React,
какую часть интерфейса приходится восстанавливать и заметна ли цена для startup/взаимодействия?
Исходники сами по себе не отвечают на эти вопросы.

### Почему стоит проверить

Изначально можно подозревать дорогую hydration или размер кода, тогда как диагностической причиной
может оказаться несовпадение серверного и клиентского дерева. Это связывает startup, hydration,
React DevTools и проверку исправления при потенциально почти неизменном размере кода.
Но ни восстановление дерева, ни его стоимость пока не измерены и не объявляются доказанными.

Это ошибка в учебном приложении, не найденный клиентский production incident.
Показывать её как необычный и дорогой performance-кейс допустимо только после проверки эффекта.
Трёхстрочный компонент сам по себе не обосновывает большой пользовательский выигрыш.

### Следующая проверка — без benchmark-серии

В изолированном примере **внутри папки доклада** воспроизвести именно недетерминированный текст
с обычным `hydrateRoot`, сохранить фактический серверный и клиентский результат и сообщение React
через `onRecoverableError`. Для диагностической проверки можно явно задать несовпадающие значения
и отдельно обозначить этот контроль; не полагаться на удачное случайное расхождение.

Результат одного шага: подтверждается ли recovery и какая граница затронута.
Пока не добавлять большой список, тяжёлую работу, задержки или повторные измерения ради желаемого эффекта.
Если эффект мал или сцена слишком очевидна, оставить коротким объяснением, а не развивать стенд.

Исправление-кандидат на будущее — согласованное начальное значение между сервером и клиентом.
До диагностики не реализуем и не обещаем ускорение.

## Отложенный кандидат: поиск с быстрыми запросами, но неверным результатом

Просмотрены `app/search.tsx`, `app/api/products/route.ts` и `lib/catalog.ts` того же учебного приложения.
Эффект зависит от вновь созданного объекта `filter`, запускает fetch и обновляет state результатом.
В коде нет проверки, соответствует ли пришедший ответ последнему запросу.
Потенциально здесь есть request loop и устаревшие ответы, но их поведение в браузере не проверялось.

Не выбираем этот сюжет на данном шаге: он добавляет отдельное расследование эффектов/сети/корректности
и не закрывает обещанную hydration. Его чтение не считается выполненным экспериментом.

## Статус кандидата mismatch

Основной веб-кейс ещё не принят. Текущий SSR-каталог и его скриншоты остаются теоретической иллюстрацией.
Воркшоп только читали, его файлы не меняли.

[Диагностика recovery выполнена](web-case/RECOVERY_INSPECTION.md): при контролируемом расхождении 7/8
в development React root проверенные заголовок, кнопка и список заменены, а при 7/7 сохранены.
Контейнер и элемент снаружи сохранены в обоих случаях. Сообщение React получено через `onRecoverableError`.
Performance-эффект не измерен.

[Production client и два диагностических traces проверены](web-case/RECOVERY_PRODUCTION.md):
в mismatch React сообщил `#418` и заменил те же проверенные узлы; в match они сохранились.
Нагрузку не увеличивали, timing-сравнение не принимали. Следующее решение — оставить материал
коротким объяснением recovery либо продолжить только при реальном пользовательском симптоме.
