# Веб-расследование

## W01. Пользовательская сцена

Пользователь открывает SSR-страницу каталога. Карточки товаров и кнопка «Сначала дешевле» уже видны.
Он нажимает кнопку и ожидает, что показанные товары сразу перестроятся по цене, но видимый ответ задерживается.
Разбираемся, почему внешне готовая страница ещё не отвечает на действие и какая работа стоит между нажатием
и результатом. После исправления повторяем то же действие: набор товаров и итоговый порядок должны сохраниться.

Это кандидат сцены для проверки, а не описание уже воспроизведённого сбоя.
Сортируем уже полученные данные: ожидание нового сетевого запроса не является частью задуманного действия.

## Что предстоит установить

- Существуют ли подходящая страница и воспроизводимый симптом на нашем стенде.
- Когда пользователь видит содержимое и когда нажимает кнопку.
- Доходит ли ввод до обработчика, как обрабатывается раннее нажатие и когда появляется результат.
- Где возникает задержка: загрузка клиентского кода, выполнение, hydration или работа после обработки ввода.

Причину, размер задержки и эффект исправления заранее не утверждаем.
Вопрос о Lighthouse и размере JavaScript проверим после воспроизведения сцены.

### Минимальный пример, необходимый для следующего шага

Одна отдельная SSR-страница с небольшим фиксированным списком товаров, ценами и клиентской кнопкой
«Сначала дешевле». Никаких запросов при сортировке, SDK, collector или viewer.
Сначала обычная работающая страница: проверить серверный HTML и поведение раннего нажатия.
Не добавлять тяжёлый цикл ради заранее желаемого результата. Если без специальных условий задержки нет,
так и записать; условия сети/CPU или изменения примера затем обсуждать явно.

Если создаём пример, его код и инструкция должны находиться внутри папки этого доклада, отдельно от воркшопа.
### Результат минимального примера

Создан [web-case](web-case/README.md): три товара, `renderToString` на сервере, `hydrateRoot` в браузере,
одна сортировка без запроса к серверу. Страница запущена на http://127.0.0.1:4350/.
Искусственная вычислительная нагрузка и задержка в код не добавлялись.

Chrome 157.0.8103.79 / Playwright проверил:

- Исходный HTML содержит товары, кнопку и первоначальный порядок.
- При обычной загрузке кнопка меняет порядок на Notebook €12 → Coffee mug €18 → Desk lamp €45.
- При контролируемом удержании `/client.js` средствами browser routing кнопка видна, но раннее нажатие
  не сортирует товары. После разрешения загрузки оно в этом примере не воспроизводится; новое нажатие сортирует.
- Page errors нет; итоговый screenshot просмотрен.

Локальные результаты и две картинки: `web-case/artifacts/browser-check.json`, `normal-sorted.png`,
`script-held-after-click.png`. Проверочный скрипт сохранён рядом как `browser-check.mjs`;
он содержит локальные абсолютные пути и не является переносимым test runner. Artifacts игнорируются Git.

**Вывод W02:** поведение минимальной SSR-страницы проверено. Естественная задержка не установлена и
не измерялась; контролируемое ожидание загрузки JS не доказывает высокую стоимость hydration.
Это пока учебный пример разницы между HTML и подключённым поведением, не принятое центральное расследование.
Дальше решаем, годится ли он для сцены, прежде чем записывать видео W03 или добавлять измерения.

### Читаемый React-код

По запросу Андрея пример переведён с `React.createElement` на обычный TSX/JSX:
[Catalog.tsx](web-case/Catalog.tsx), [client.tsx](web-case/client.tsx), [render.tsx](web-case/render.tsx).
Общий компонент использует `useState`, `onClick` и JSX; сервер и клиент компилируются при запуске.
TypeScript-проверка и повторный Chrome check прошли: HTML содержит каталог, сортировка работает,
результат раннего клика при удержании JS тот же, page errors нет. Это изменение формы кода,
новых performance-выводов оно не добавляет.

## Проверка с ограничением сети и CPU

[Один диагностический прогон и сохранённый trace](web-case/LOAD_INSPECTION.md):
FCP 316 ms, ранний click 419.7 ms, JS responseEnd 1444.4 ms. Первое действие потерялось,
следующее после загрузки сработало. Использовали эмуляцию сети/CPU, без ручного удержания JS request.
Клиентский JS отдаётся без сжатия; это существенное условие примера.
Причину раннего пропущенного нажатия объясняет ещё не загруженный клиентский код;
дорогая hydration не установлена. Пока кандидат подходит как теоретическая иллюстрация,
а не как принятое основное расследование. До записи W03 пересматриваем роль этой сцены.
