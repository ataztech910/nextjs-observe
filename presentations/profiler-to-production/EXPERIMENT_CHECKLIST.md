## 1. Веб — «Страница видна, почему кнопка ещё не отвечает?»

Вывод, который проверяем: появление содержимого и готовность к взаимодействию — разные события.
Конкретную причину ещё предстоит установить, не объявляем её заранее hydration.

- [x] W01. Описать одну сцену: какая страница, что видит пользователь, какую кнопку нажимает,
  какого результата ждёт. **Результат:** [каталог и сортировка по цене](WEB_CASE.md), без реализации нового стенда.
  Это кандидат для проверки, симптом пока не подтверждён.
- [x] W02. Найти подходящую существующую SSR-страницу и проверить сцену в браузере.
  **Результат:** путь/команда запуска и наблюдение — воспроизводится ли задержка.
  Если подходящей страницы нет, сначала описать минимально необходимый пример.
  [Готовой сцены нет; создан и проверен минимальный SSR-пример](WEB_CASE.md).
  Chrome/Playwright проверил исходный HTML, обычную сортировку и ранний клик при удержании JS request;
  скриншот просмотрен. Естественная задержка не установлена. Это завершение проверки, не принятие кейса.
- [ ] W03. Сохранить короткую запись симптома с условиями запуска.
  **Результат:** видно действие пользователя и задержанный результат, а не только итоговую таблицу.
  Сохранены [скриншоты приложения и настоящей Chrome Performance panel](web-case/figures/README.md),
  собран и вставлен теоретический кадр в текущий `slide-02`. Видео действия пока нет;
  диагностический пример не принят как центральное расследование.
- [ ] W04. Определить границы измерения: появление содержимого, запуск клиентского кода,
  наблюдаемые границы hydration, ввод и ответ на действие. **Результат:** простая схема с источником
  каждого события; что нельзя измерить выбранным способом — явно отметить.
- [ ] W05. Снять диагностический профиль и пройти по нему в React DevTools.
  **Результат:** выделенная работа и соответствующий код; отделены ожидание JS, выполнение,
  hydration и последующий render. Если React DevTools недостаточно, использовать browser trace.
- [ ] W06. Сформулировать причину и одно предлагаемое исправление.
  **Результат:** «задержка возникает из-за …; меняем …; ожидаем …» с опорой на профиль.
  Проверить, достаточно ли здесь интересного материала для центрального кейса.
- [ ] W07. До сравнительных запусков записать короткие условия: что сравниваем, основной endpoint,
  повторы, порядок, условия загрузки и причины невалидного запуска.
  **Результат:** воспроизводимый план без новой системы протоколов.
- [ ] W08. Сохранить исходный вариант и выполнить исходные повторные измерения.
  **Результат:** версия кода, условия и отдельные результаты; диагностический профиль не смешан с timing runs.
- [ ] W09. Внести одно исправление и проверить сохранение поведения.
  **Результат:** небольшой diff; пользователь получает тот же результат, необходимая работа не пропала.
- [ ] W10. Повторить сравнение исходного и исправленного вариантов по записанным условиям.
  **Результат:** все результаты и разброс, влияние на действие и startup; проверить, не перенесена ли задержка.
- [ ] W11. Проверить роль Lighthouse и bundle size именно в этой сцене.
  **Результат:** реальные load results и bytes рядом с пользовательской метрикой.
  Не обещать заранее score 100 или одинаковый размер; старые A/B не выдавать за измерения нового кейса.
- [ ] W12. Собрать историю из пяти частей: симптом → измерение → причина → исправление → результат.
  **Результат:** короткий текст и выбранные кадры для слайдов 08–12; решение, годится ли кейс в доклад.

## 2. React Native — «React рендерит быстро, почему действие задерживается?»

Вывод, который проверяем: короткий render не означает свободный JS thread.
Кандидат причины — пересчёт общей истории при progress events загрузок. Hermes уже дал диагностическую
зацепку; надёжного пользовательского before/after пока нет. Предыдущий inconclusive результат сохраняем.

- [ ] R01. Описать одну сцену во время загрузок: действие пользователя и ожидаемый ответ.
  **Результат:** короткий абзац, выбранный endpoint и отличие от веб-расследования.
- [ ] R02. Вручную проверить сцену на существующем RN-приложении.
  **Результат:** воспроизводимый симптом и запись; указаны Simulator/устройство и тип сборки.
- [ ] R03. Разобрать сохранённые Hermes profiles и код обработки progress.
  **Результат:** конкретный стек и объяснение, что уже доказано, а что осталось гипотезой;
  новый capture нужен только при недостаточности существующего.
- [ ] R04. Проверить тезис про быстрый React render на той же сцене.
  **Результат:** реальный React profile рядом с JS-диагностикой. Если тезис не подтверждается,
  изменить формулировку кейса, а не подбирать удобную картинку.
- [ ] R05. Выбрать одно изменение и объяснить сохранение работы.
  **Результат:** конкретное сравнение, например полный rescan против incremental update;
  сохраняются необходимые события, данные и конечный результат.
- [ ] R06. Записать минимальный план Release-сравнения: endpoint, нагрузка, повторы, порядок,
  условия устройства и validity rule. **Результат:** учтена причина невалидности прошлого исследования;
  если сопоставимость обеспечить нельзя, не начинать очередную серию.
- [ ] R07. Провести сравнение по плану и сохранить все исходы.
  **Результат:** пользовательская задержка до/после, разброс и выполненная работа;
  Debug/Hermes диагностика отделена от Release timing. Неподтверждение улучшения — допустимый итог.
- [ ] R08. Отдельно определить и измерить RN startup.
  **Результат:** native launch → usable с явными cold/warm условиями и повторными запусками;
  не приписываем startup причину из progress-кейса без доказательств.
- [ ] R09. Проверить доступный путь настоящего запуска Flashlight.
  **Результат:** поддерживаемая Android-среда и возможность выполнить сценарий.
  Сейчас подтверждён только iPhone; если доступа нет, записать блокер и обсудить его до подготовки показа.
- [ ] R10. При доступной среде получить Flashlight report и разобрать один полезный показатель.
  **Результат:** настоящий отчёт с условиями; не смешивать его числа с iOS-сравнением.
- [ ] R11. Собрать RN-историю для слайдов 13–18.
  **Результат:** симптом, профиль, изменение и честное before/after; startup и Flashlight имеют
  понятную роль. Если пользовательский выигрыш не доказан, кейс не отмечаем готовым.
