## 1. Framework выбора метрик

19 ноября: [вступление и послайдовый текст](speaker-guide/framework-metrics.md)
объясняют переход от проблемы к вопросам пользователя, границам измерений и общей схеме.
Ранее объединённые слайды восстановлены; тайминг не ограничивает содержание.
[Отдельный RN framework](speaker-guide/framework-native.md)
открывает RN-часть после Web-примеров. Сейчас разбираем только framework;
его согласование и применение к принятым Web/RN расследованиям ещё впереди.

Зритель должен уметь начать с пользовательской задачи, выбрать событие начала/конца и источник,
а затем объяснить, что число позволяет решить и чего в нём не видно.

Показ: карта «пользовательский вопрос → метрика → граница → источник → решение» отдельно для Web
и в начале RN-части; возвращение к ней в соответствующих кейсах и в завершении. TTI, startup, hydration cost, JS jank остаются
в обещанном охвате; внутреннее вычисление не подменяет ответ/показ результата пользователю.

Lighthouse score, bundle bytes и React render duration не объявляем бесполезными сами по себе.
Vanity здесь — оптимизация proxy-числа без проверки выбранного пользовательского результата.
Лабораторный пример показывает конкретное расхождение наблюдений, не доказывает универсальную
корреляцию со всей аудиторией production-приложений.

**Критерий готовности:** после каждого кейса понятно, какое решение изменила выбранная метрика.
Таблица красивых чисел без связи с симптомом этот результат не закрывает.

## 2. Toolkit выбора инструмента

Нужны реальные проходы, в которых инструмент отвечает на конкретный вопрос:

- React DevTools — разбор работы React в выбранном кейсе и границ его показателей.
- Hermes profiler — разбор JS-стека RN-кейса.
- Flashlight — дополнительное наблюдение на поддерживаемой Android-среде, отдельно от iOS данных.
- Custom instrumentation — фиксация явно определённого действия/события, которого не хватает для вывода.

Это требования к показу, не заявление, что каждый проход уже подготовлен.
Измерение сверяем с независимым подходящим источником, когда он доступен. Название «ground truth»
не делает наш marker точным временем paint, полной CPU-стоимостью или показанием физического устройства.

OpenTelemetry передаёт выбранные наблюдения и контекст в совместимый backend; backend используется
для повторного чтения и постоянного наблюдения. OTel не заменяет профайлер и не выбирает метрику за нас.

**Критерий готовности:** зритель понимает, когда открыть каждый инструмент и как пройти от симптома к причине.
Список логотипов, Profiler API вместо реального DevTools walkthrough или replay вместо live RUM недостаточны.

## 3. Применимый CI template

Зритель должен получить рабочую заготовку для своего репозитория, а не только совет «добавьте performance в CI».

Минимальный комплект внутри папки доклада, когда будет реализован:

- workflow с запуском выбранного воспроизводимого сценария;
- baseline и явное правило сравнения с учётом наблюдаемого разброса;
- команда с понятным exit code и сохранением машиночитаемых результатов;
- artifacts: отдельные прогоны и понятный отчёт; диагностический профиль при необходимости;
- пример нормального исхода и намеренной регрессии, которая нарушает performance rule;
- инструкция по разбору failure, нестабильному измерению и согласованной смене baseline.

**Критерий готовности:** шаблон применён на нашем сценарии; проверены нормальный и намеренно медленный варианты.
Функциональный assertion и тесты самого harness не заменяют performance regression.
Backend/OTel помогает наблюдать приложение после релиза, CI ловит выбранные регрессии до него — нужны обе части.
