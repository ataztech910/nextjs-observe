# От вопроса доклада к framework: связное вступление

Актуальный порядок после уточнения Андрея, 19 ноября 2026.
Тайминг не определяет объём этого материала. Сокращения и подачу определяет Андрей.
При добавлении общей схемы сохраняем самостоятельные объясняющие слайды.

## Логика перехода после самопрезентации

Знакомство со спикером → почему привычных чисел недостаточно → чего ждёт пользователь →
как задать границы измерения → что позволяет заключить каждое число → общий порядок расследования.
Framework — итог этой аргументации, а не исходное требование без объяснения.

Восстановлены отдельные карточки «Which wait are we measuring?» и Web-карта измерений.
Общая схема сохранена своей карточкой; перед ними добавлена постановка проблемы на материале
существующих исследований. Новых экспериментов и бытовых кейсов для этого перехода нет.

## 1. The report looks fast. What did the user experience?

ID: `performance-question`. [Открыть слайд](http://127.0.0.1:4349/#step=performance-question).

**На экране:**

- Content can be visible before the action we need is usable.
- The same JavaScript size can accompany different executed work.
- A short React render can be followed by expensive browser layout.
- Before trusting a number, we need to know which user question it answers.

**Что говорю:**

После знакомства со мной перейдём к вопросу самого доклада. Мы открываем DevTools и получаем много чисел. Но какое из них говорит о том, чего ждёт человек?

В подготовленных примерах HTML уже виден, а раннее действие ещё не работает. Объём JavaScript одинаковый, а исполняемой работы разное количество. React render короткий, но браузер продолжает пересчитывать layout. Данные не обязательно ошибаются: мы можем ожидать от них ответа на другой вопрос.

Поэтому сначала разберём, что именно значит «быстро» для пользователя. Затем посмотрим, что позволяют заключить привычные метрики. И только после этого соберём общий порядок измерения.

## 2. Which wait are we measuring?

ID: `user-waits`. [Открыть слайд](http://127.0.0.1:4349/#step=user-waits).

**На экране:**

- Opening: when can I actually start using the screen?
- Acting: when will I see the correct result of my input?
- Moving: does scrolling or animation continue without interruptions?
- These are different outcomes; one number cannot stand in for all three.

**Что говорю:**

Слово «быстро» прячет несколько вопросов. При открытии приложения я жду, когда смогу им пользоваться. После нажатия жду правильный результат. При скролле хочу, чтобы движение не прерывалось.

Это три разных свойства. Экран может быстро появиться, но поздно начать отвечать. Он может отвечать на кнопку, но дёргаться при движении. Сейчас мы ещё не выбираем инструмент — называем то ожидание, которое хотим исследовать.

## 3. Web: three questions, different measurements.

ID: `framework-map`. [Открыть слайд](http://127.0.0.1:4349/#step=framework-map).

**На экране:**

- Open: navigation → defined usable state. Verify a representative action; state network and cache conditions.
- Act: input → visible correct result. Name the source that observes the endpoint.
- Move: browser frame timing during the selected scroll or animation.
- Legacy TTI is a specific web lab metric; an app-ready marker is a different measurement.

**Что говорю:**

Теперь связываем эти вопросы с измерением на вебе. Для открытия называем событие навигации и проверяемое usable состояние. Для действия называем input и наблюдение результата. Для движения — участок сценария и источник frame timing.

Название метрики ещё не определяет её границы. Первый React effect не доказывает, что нужное действие уже работает. И обещанный TTI — конкретная legacy lab-метрика, удалённая из Lighthouse 10, а не любое время до нашего marker готовности.

Для React Native этот перевод сделаем отдельно, когда дойдём до мобильной части.

## 4. What can this number prove?

ID: `framework-proxies`. [Открыть слайд](http://127.0.0.1:4349/#step=framework-proxies).

**На экране:**

- Lighthouse score → the load audit under its stated conditions; test later actions separately.
- Bundle size → code volume; inspect the work that actually executes.
- React actualDuration → rendering in the profiled tree; inspect the rest of the path to display.

**Что говорю:**

Lighthouse отвечает про загрузку в условиях аудита. Последующее действие проверяем отдельно.
Размер бандла говорит об объёме кода. Сколько работы исполнится, нужно выяснить.
React actualDuration показывает render профилируемого дерева. До результата на экране есть и другая работа.

Эти числа полезны. Vanity target получается, когда улучшение одного из них принимают за пользовательскую
победу без проверки действия. Поэтому правило такое: профилем ищем причину, а исправление принимаем
по повторному измерению того же результата с сохранённой корректностью и работой

## 5. Choose the metric. Find the cause. Verify the gain.

ID: `framework-choice`. [Открыть слайд](http://127.0.0.1:4349/#step=framework-choice).

**На экране:**

- Outcome: choose what the user waits for and define one primary metric.
- Diagnosis: profile the work and identify a testable cause.
- Decision: repeat the same task, preserve correctness and work, compare the primary metric.

**Что говорю:**

Из этих вопросов теперь получается общий порядок действий. Соберём его на одном экране. Слева выбираем, чего ждёт пользователь, и одну основную метрику с понятным началом и концом. В центре ищем работу, которая объясняет ожидание: это диагностические измерения. Справа после изменения повторяем ту же задачу и по основной метрике решаем, принимать исправление или нет. Корректность, объём работы и условия сохраняем.

Нижняя строка — уже наш пример. Человек разворачивает 120 карточек. Выбираем browser Event Timing как наблюдение отклика. Render короткий, а Chrome trace показывает повторный layout. Меняем порядок операций и снова измеряем: во всех шести локальных парах отклик меньше, медианы 88 и 64 миллисекунды, итог тот же.

То есть метрика результата отвечает, стало ли лучше, а диагностические числа помогают понять, что менять. Для Web и Native порядок один; конкретные источники разберём в соответствующих частях.

## Карта для подготовки, а не третий слайд

| Вопрос | Наблюдение результата | Где искать причину | Чего не заключаем автоматически |
| --- | --- | --- | --- |
| Когда можно начать? | Navigation → определённое usable состояние, проверенное ключевым действием | Загрузка, исполнение JS, hydration, React и browser rendering | Первый effect или видимый HTML ещё не доказывают готовность действия |
| Когда получу ответ? | Названный input → наблюдаемый правильный результат; источник endpoint указан | Ожидание JS, обработчик, вычисления, React, layout и paint | React callback не является временем показа результата |
| Почему движение прерывается? | Browser frame timing на заданном участке движения | Main-thread work и отрисовка браузера | Средний FPS не описывает все отдельные прерывания |

В кейсах используем эту карту для выбора следующего шага. Не повторяем её определения перед каждым профилем.
[Layout-разбор](web-layout-framework.md): гипотеза о React → проверка render → повторный layout → изменение порядка операций.
[RN-разбор](framework-native.md) использует свои platform boundaries.

## Технические границы для подготовки и Q&A

- Hydration cost требует локализовать работу hydration. Всё ожидание клиентского JS не является её CPU стоимостью;
  возврат `hydrateRoot` не служит универсальным концом hydration.
- Browser Event Timing имеет собственную границу и не подтверждает автоматически показ конкретного асинхронного
  результата. Одна click duration не является полевым INP всей страницы.
- React `actualDuration` описывает render профилируемого дерева, а не все возможности React DevTools.
- Для сравнения фиксируем build, устройство, сеть/cache, сценарий, источник сигнала и разброс повторов.
  Сохраняем правильность, необходимый объём работы и ошибки; недоступный сигнал не заменяем нулём.
- Это предлагаемая карта выбора. Лабораторная длительность не доказывает универсальную корреляцию с конверсией,
  удержанием или удовлетворённостью. Соответствие endpoint задаче нужно обосновать.
- Legacy TTI — конкретная lab-метрика, удалённая из Lighthouse 10; произвольный app-ready marker не является TTI.
  Это уточнение остаётся в подготовке и должно быть объяснено при обсуждении готовности в Web-кейсе.

Источники определений и ограничений:

- [TTI и удаление из Lighthouse 10](https://web.dev/articles/tti).
- [React Profiler и actualDuration](https://react.dev/reference/react/Profiler).
- [hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot).
- [Lighthouse performance scoring](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring).

## Что проверяем при просмотре

- Понятно, зачем после самопрезентации говорим об измерениях.
- Различимы пользовательское ожидание, наблюдающая его метрика и диагностические числа.
- Общая схема отвечает на вопросы, уже поставленные в предыдущих карточках.
- Сокращения не выполняются ради тайминга; содержание и подачу просматривает Андрей.

Добавление вступления не меняет сохранённые результаты и не закрывает toolkit, RN before/after и CI.
