# 25 · The screen is closed. Its handlers are not.

`step: rn-subscription-fix` · RN: экрана нет, работа идёт · **16:50 → 17:40** (0:50)

**На экране:** график: по горизонтали визиты, по вертикали JS-время на одно обновление. Оранжевые столбцы без отписки — 0,45 → 4,3 → 12,4 мс (среднее 4 Release-прогонов), белые точки — отдельные прогоны. Зелёные — после исправления, около нуля. Пунктир 16,7 мс — ориентир кадра 60 Hz.
**Задача слайда:** показать цену ошибки и цену исправления в одной картинке. Повернуть к покупателю: больше всего лишней работы у того, кто чаще всех заходит в заказы. Честно сказать, что задержку нажатия мы не мерили.

## Текст

Вот цена этой ошибки. *(провести по оранжевым столбцам)* Сколько JavaScript выполняется на одно обновление, когда все экраны закрыты.

После одного визита — меньше половины миллисекунды. После десяти — четыре. После тридцати — двенадцать с лишним. Сборка Release, четыре прогона, это среднее.

Экран один и тот же, закрыт он одинаково. Растёт только число визитов. Значит, больше всего лишней работы — у самого активного покупателя, у того, кто чаще всех заходит проверить заказ.

Теперь исправление. В `useEffect` возвращаем функцию, которая отписывает обработчик. Одна строка. *(показать зелёные столбцы)* Тот же опыт: ноль подписок, ноль вызовов, время около нуля — на любом числе визитов.

Почему это касается пользователя? JavaScript в React Native выполняется в одном потоке. Пока работают эти обработчики, всё остальное в этом потоке ждёт — в том числе обработка нажатия, если оно пришло в этот момент.

Но честно: задержку нажатия этот график не показывает. Мы измерили лишнюю работу JS, а не то, насколько позже покупатель увидел результат. Пунктир на 16,7 миллисекунды — это длительность кадра для ориентира, а не порог, по которому мы что-то считали.
