# Web: короткий React render, дорогой layout, проверенный отклик

Обновлено 19 ноября 2026 после шести заранее описанных пар.
Порядок: `mini-layout` — диагностические Chrome traces → `layout-framework-check` — все шесть пар Event Timing.
[Открыть результат](http://127.0.0.1:4349/#step=layout-framework-check).

## Что зритель расследует

Пользователь нажимает «Expand cards to full width» и ждёт, когда те же 120 карточек развернутся.
Сохраняем текст, порядок и конечные размеры. Это контролируемый React/DOM-пример,
а не выдуманная история production incident.

Проверяем гипотезу «ожидание объясняется дорогим React render». Это вопрос зрителю,
а не утверждение о том, что мы исторически так диагностировали чей-то инцидент.

## Первый кадр — где искать причину

На `mini-layout` показываем сохранённые Chrome Performance screenshots.
React update actualDuration короткий: 4.2 / 4.5 ms. В trace видны повторные layout при чередовании
чтения `container.offsetWidth` и записи ширины каждой карточки.

Изменение: прочитать ширину один раз перед теми же 120 записями.
Layout events внутри effect: 120 / 1; во всём записанном окне после handler: 121 / 2.
Поздний layout не скрыт за границей effect. Конечные карточки совпадают.

**Что говорю:**

«Проверим гипотезу: может, действие ждёт из-за дорогого React render?
Здесь render короткий в обоих вариантах. Значит, продолжаем смотреть trace.
Видна другая работа: чтение ширины чередуется с записью стиля, браузер повторяет layout.
По этим данным следующий шаг — изменить порядок DOM-операций: одно чтение, затем те же записи.
Теперь нужно проверить, изменился ли отклик на нажатие».

## Второй кадр — что изменилось для выбранного действия

`layout-framework-check` показывает диаграмму всех шести пар. Browser Event Timing interaction maximum:

| Пара | Interleaved, ms | Batched, ms | B−I, ms |
| --- | ---: | ---: | ---: |
| 1 | 88 | 64 | −24 |
| 2 | 88 | 64 | −24 |
| 3 | 80 | 64 | −16 |
| 4 | 80 | 64 | −16 |
| 5 | 176 | 64 | −112 |
| 6 | 88 | 64 | −24 |

Медианы 88 → 64 ms. Во всех шести парах направление одинаковое, 0 missing и 0 invalid.
Порядок вариантов чередовался, каждый click — отдельный свежий Chrome process.
Все 120 карточек сохранили одинаковый текст, порядок и конечные размеры.

**Что говорю:**

«Мы повторили действие в шести парах, меняя порядок вариантов. После изменения наблюдённый отклик
меньше во всех шести: медианы 88 и 64 миллисекунды, результат работы тот же.
Пятая пара с 176 миллисекундами тоже здесь — мы её не исключали.
Это локальный browser Event Timing, не полевой INP и не точное время физических пикселей.

Практический вывод: короткий React render не заканчивает расследование.
Здесь профиль привёл к порядку DOM-операций, а повторное измерение подтвердило одно направление
изменения выбранного endpoint. Именно так карта выбора метрик помогает принять решение».

## Четыре ответа по framework

| Вопрос | Ответ по существующему кейсу |
| --- | --- |
| Что пользователь ждёт? | Развёрнутые правильные карточки после нажатия |
| Чем наблюдаем отклик? | Max duration наблюдённых pointerdown/up/click одного interactionId; endpoint браузерного Event Timing |
| Что объясняет работу? | Отдельный Chrome trace показывает повторный layout; actualDuration не описывает весь этот путь |
| Что принимаем? | Во всех шести локальных парах browser endpoint меньше при том же результате; не переносим величину эффекта на другие устройства и пользователей |

## Подготовка и Q&A

- [Полная серия, условия и ограничения](../web-case/LAYOUT_COMPARISON.md), [все raw данные в JSON](../web-case/layout-comparison-result.json).
- [Диагностическая пара](../web-case/LAYOUT_INSPECTION.md) записана отдельно с tracing:
  4.2/4.5 ms render и 39.483/3.199 ms effect не принадлежат новым двенадцати нажатиям.
- Пилот 120/96 ms не входит в шесть пар. Duration имеет гранулярность 8 ms, observer threshold 16 ms.
- Final DOM подтверждает правильный итог, но не точный presentation timestamp. Здесь синхронное изменение;
  не превращаем этот endpoint в универсальный измеритель готовности любого асинхронного действия.
- Причина значения 176 ms не изолирована; весь разрыв нельзя назвать CPU стоимостью layout.
- Headless Chrome, CPU 4×, production profiling build. Это локальное directional observation,
  не статистический population claim, physical UX acceptance или готовый CI budget.
- Кейс приобрёл повторное сравнение; RN, toolkit, CI и весь доклад этим не завершаются.
