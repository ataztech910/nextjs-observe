# План воркшопа — AI-Native Observability

**Тема:** Building Self-Debugging Next.js Applications with OpenTelemetry
**Дата:** 10 ноября 2026, Португалия. **Длительность:** 3 ч 30 мин, смешанная аудитория.
**Формат:** гибрид. Участники работают только локально; прод (Vercel + дроплет) — демо ведущего, поднимается заранее.

**Слова** (как в README пакетов): **APM-агент** — `next-observe`, библиотека внутри приложения, только OpenTelemetry; **AI-агенты** — ADK-агенты внутри обзервера; **обзервер** — `next-observer` целиком (сервер, UI, детектор, проверки по расписанию, AI-агенты), запускается через `npx`. Просто «агент» не говорим — зал путает.

**Приложение:** Porto Shop. Старт — `master` (= тег `block-2-start`): голый Next 16 без телеметрии. Состояния блоков — теги `block-2-init`, `block-3-instrumentation`, `block-4-agents`; отставший делает `git stash -u && git checkout -B workshop <тег> && npm install`. Дома: `npm install` и `npm run doctor` — после «All set» всё работает без Wi-Fi.

## Лесенка: от «не работает кнопка» до «упал прод»

Порядок — от того, что знакомо любому фронтендеру, к тому, что обычно видит только эксплуатация. Каждая ступень отвечает на вопрос, который оставила предыдущая.

| Уровень | Что ломается | Где в магазине | Что видит пользователь | Что показывает обзервер | Блок |
|---|---|---|---|---|---|
| 1. JavaScript | исключение в обработчике клика | «♡ Save for later» | кнопка не работает | Errors: `uncaught error`, Cannot read properties of null (reading 'push'), страница | 2a |
| 1 | ошибка рендера, пойманная `error.tsx` | «Show details», товар 4 | «Something went wrong» | Errors: `console.error`, «occurred in the `<Details>` component» | 2a |
| 1 | расхождение гидратации | «N people are looking» | ничего | Errors: `hydration mismatch` — `<Viewers>` → `<p>`, `+ 30 / − 5` | 2a |
| 1 | ответ не JSON | отзывы, товар 2 (API отвечает 204) | вечное «Loading reviews…» | Errors: `invalid JSON response`; сервер «здоров» | 2a |
| 2. API | фронт и бэк расходятся в правилах | количество 20 при лимите 10 | «Payment failed» без причины | Errors: запрос браузера `POST /api/checkout` — HTTP 400 | 2a |
| 3. Состояние | эффект → `setState` → эффект | поиск в каталоге | ничего, поиск «работает» | Overview: `GET /api/products` — 65% всех запросов | 2a |
| 4. Структура | N+1 | каталог (`lib/catalog.ts`) | «чуть медленно» | после `'use observe'`: 5 одинаковых `getProductById` в waterfall | 3 |
| 5. Деплой | регрессия в v2 | платёж (`lib/payment.ts`) | оплата 2 секунды вместо 0.2 | баннер регрессии, страница операции (две версии), Latency Agent | 4 |
| 5 | нестабильная зависимость | склад, 30% отказов | иногда «stock unavailable» | детектор → AI-агенты сами; Errors: `checkInventory` | 4 |
| 6. Последний рубеж | то же, но ночью и без пользователей | `observe.checks.ts` | — | Checks: «checkout takes under a second» красная в v2 → аномалия → расследование | 4 |
| 7. Данные врут | быстрый ответ без ошибки, а данные чужие | инцидент F вживую: тег `block-5-incident-f`, `npm run dev:v3` | открыл товар 1 — показали товар 3 | Overview зелёный; аномалия `data_integrity` «asked for "1", got back "3"»; на трейсе плашка «Wrong data» | 5 |

**Как вести блок 2a (30 минут).**
1. *5 мин.* Все открывают магазин и просто пользуются им: товар 1 — «Save for later», количество 20 — Buy; товар 2; товар 4 — «Show details»; поиск на главной. В DevTools не смотрим.
2. *5 мин.* Открываем Errors в обзервере. Вопрос залу: «сколько багов вы заметили руками и сколько здесь?» Гидратацию и цикл запросов руками не замечает никто.
3. *15 мин.* Чиним два-три: «Copy prompt» с карточки → Claude Code / Codex (или руками). Рекомендуемые: `null.push` (одна строка), 204 → `[]`, цикл запросов (объект в зависимостях эффекта).
4. *5 мин.* Что не починили: 400 от API — причина осталась в теле ответа, в спанах её нет. Мостик к блоку 3: «чтобы видеть причину, её надо положить в спан».

**Слайд из практики.** AI-ревью в pre-commit нашло пять из этих шести багов и заблокировало коммит; расхождение гидратации — не нашло: оно видно только при исполнении. Ревью кода и наблюдаемость ловят разное.

**Мостик к блоку 4 (проверки).** В блоке 4 запускаем магазин как v1, потом как v2, **не включая нагрузку**: проверка «checkout takes under a second» краснеет сама, в чате появляется аномалия. Вопрос залу: «кто из ваших пользователей сообщил бы об этом в три часа ночи?»

**Финал блока 5: инцидент F вживую (5–7 минут).** Тег `block-5-incident-f` — блок 4 плюс «выкатка» v3.
1. Обзервер запущен, магазин — `npm run dev:v2`, нагрузка `npm run load 40`: в чате аномалия про медленный checkout. «Чиним»: останавливаем v2, `npm run dev:v3`, снова нагрузка.
2. Показываем Overview: ошибок нет (кроме привычного склада), checkout снова быстрый. «Починили?»
3. Открываем в браузере `/product/1` несколько раз под нагрузкой — иногда это не кружка. Статус 200, 20 мс.
4. В чате — «Wrong data · 3 responses came back wrong»: asked for "1", got back "3". Открываем трейс: плашка «Wrong data», метка на спане `getProductById`, событие `integrity_check` (expected / actual).
5. Показываем код: `lib/pool.ts` (30 строк — пулер в transaction-режиме отдаёт ответы не по порядку) и одну строку в `lib/db.ts`, где приложение само спрашивает «я получил то, что просил?».
6. Вывод: автоинструментация этого не видит и не может — приложение должно решить, что это стоит измерить. История двух суток и шести «починок» — из `APM_FINDINGS.md`.

Проверка «product 1 is the mug» в `observe.checks.ts` за короткий прогон не падает: одиночный запрос снаружи почти никогда не попадает в путаницу. Это тоже говорим вслух — внешняя проба ловит такое только случайно.

**Что говорить про границы.** Проверки по расписанию — для доступности, времени ответа и инвариантов («гость получает 401», «99 штук — это 400»). Сканер уязвимостей и нагрузочный тест в проде сюда не тянем.

## Сценарий блоков 0–2: как подать историю

Каждый шаг отвечает на вопрос, который сам же поставил предыдущий — так теория выглядит не лекцией, а необходимостью.

**0. Боль, с которой начинаем — простая.** Не инцидент с пулером БД, а кнопка: «у пользователя не работает „Сохранить“. В вашей консоли ошибок нет — она в *его* браузере. Как вы узнаете?» Инцидент F (страница отдаёт 200 за 50 мс, а данные чужие — `APM_FINDINGS.md`) оставляем на финал блока 5: к тому моменту зал уже видел, что статус и латентность ловят многое, и готов к случаю, где они молчат.

**1. Теория: трейс → OTel (слайды, 25 мин).**
- Спан = «что происходило, сколько, с какими атрибутами» — дерево вызовов во времени, не замена логов.
- Ключевой тезис: **данные и то, куда они уходят, — разные вещи**. OTel — протокол (OTLP) + SDK; SDK экспортирует спаны одинаково, кто бы их ни читал.
- Альтернативы называем прямо: Grafana (Tempo/Loki), Dynatrace, Honeycomb, Datadog — все слушают тот же OTLP.
- Два слова про слова: APM-агент (в приложении) и AI-агенты (в обзервере) — разные вещи.

**2. Настройка (10 мин, руками).** `npx next-observer init` → `npm run observe` на голом Porto Shop. Спаны в UI через секунды. Сразу после — блок 2a: телеметрия уже есть, ничего дописывать не надо, а шесть багов видно.

**3. Поворот: «а дальше это всё равно нужно куда-то агрегировать».** `next-observer` — одновременно backend, UI и AI-агенты, но в проде вы скорее отправите те же спаны в Grafana или Dynatrace. Для воркшопа берём его, потому что:
- это тот же протокол — в инструментации нет ничего обзервер-специфичного;
- в нём есть **AI-агенты, работающие локально** над теми же данными, и это можно показать за 3,5 часа без внешнего сервиса и лицензий.

## Кейсы для блока агентов (реальные, воспроизводимые)

Взяты из проверки ADK + Kitana (журнал, шаг 10). Скрипты лежат в `spikes/adk-kitana/`. Каждый кейс — это «сломали → увидели → исправили → поняли принцип». В блоке 4 их можно показать за ~10 минут или дать участникам повторить.

### Кейс 1. «Агент сдался» — проектирование инструмента важнее промпта

- **Вопрос:** «Checkout is slow. Which operation and which deployment caused it?»
- **Что произошло:** агент вызвал `get_operation_stats({ operation: "checkout" })`. Операции с таким именем нет, есть `chargePayment`. Инструмент вернул `[]`, и агент ответил «данных нет».
- **Исправление в инструменте, а не в промпте:** при пустом совпадении возвращать все операции с пометкой `note: "no operation matches …, showing all"`. После этого 2 из 2: агент сам связал checkout → `chargePayment`, нашёл `v2`, привёл точные p50/p95/p99.
- **Принцип:** пользователь говорит на языке бизнеса, спаны — на языке кода. Инструмент должен помогать модели сопоставить их, а не ставить ей подножку пустым ответом.

```bash
npm run agent   # в spike.mjs можно вернуть фильтр без fallback и увидеть провал
```

### Кейс 2. «Уверенная галлюцинация» — оркестратор на неполных данных

- **Вопрос:** «Users say checkout is slow and product pages sometimes fail. What is going on?»
- **Что произошло (1 прогон из 3):** оркестратор вызвал обоих специалистов, но специалист по латентности не выполнил свой инструмент. Оркестратор всё равно написал уверенный отчёт: «checkout медленный, *скорее всего*, из-за того же inventory». Этого в данных нет, это две независимые проблемы.
- **В удачных прогонах (2 из 3):** обе проблемы названы **независимыми**, с точными цифрами и текстом исключения.
- **Принципы:**
  - отчёт — только из фактов, которые вернули инструменты. Если данных нет, так и сказать, без догадок;
  - LLM недетерминирована: один прогон ничего не доказывает. Нужны **evals** — автоматические проверки ответа, как в наших скриптах (PASS/FAIL по фактам);
  - это аргумент в пользу DSL и структурированного вывода (карточки с полями) вместо свободного текста.

```bash
npm run orchestrator   # запустить 3–5 раз и сравнить отчёты
```

### Кейс 3. «Агент заговорил по-русски» — промпт адаптера протекает в ответ

- **Что произошло:** при английском вопросе и английской инструкции один из ответов пришёл на русском.
- **Первая гипотеза (неверная):** «Kitana запускает личный `claude` CLI участника, и его настройки протекают в агента».
- **Настоящая причина — в коде адаптера.** `@kitana-sdk/adk` описывает модели инструменты и пересказывает историю вызовов **по-русски**: «Доступные инструменты (JSON Schema)…», «Если нужно вызвать инструмент, ответь ТОЛЬКО валидным JSON…», «Вызов инструмента …», «Результат вызова …». Модель подхватывает язык контекста.
- **Исправление:** промпт адаптера на английском или нейтральный по языку; до этого — явное `Answer in English` в инструкции каждого агента.
- **Принципы:**
  - агент — это модель плюс **всё**, что попадает ей в контекст: инструкция, системный промпт адаптера, пересказ истории;
  - первую правдоподобную гипотезу надо проверять: мы нашли причину, только прочитав код адаптера;
  - провайдер-адаптер — часть поведения агента, и его надо тестировать так же, как свой код.

### Кейс 4. «Агент не заглянул внутрь» — N+1 видно только в трейсе

- **Вопрос:** «The product catalog is slower than expected but no single span stands out. What is wrong?»
- **Удачно (4 из 5):** `search_traces` → `get_trace` → `repeated: count=5, totalMs=90` → «N+1 confirmed: 5 identical db.query calls… should be batched».
- **Неудачно (1 из 5):** специалист ограничился статистикой (p50 = p95 = p99 = 120 мс, регрессии нет) и не открыл ни одного трейса. Вывод: «узкого места не нашли».
- **Принципы:**
  - агрегаты не показывают **структуру**: N+1 виден только внутри трейса. Инструмент, который сам находит повторы (`repeated`), превращает поиск иголки в одно поле ответа;
  - в инструкции специалиста надо явно просить «открой пример трейса»;
  - один и тот же вопрос даёт разные траектории, поэтому evals гоняют много раз.

```bash
OBSERVE_AI=real npx vitest run e2e/investigate.real.test.ts --silent=false   # протокол каждого шага
```

## Стартовый репозиторий: Porto Shop

Репозиторий `workshop-ai-observability`. Баги — в таблице «Лесенка» выше: шесть фронтенд-багов (в `master`, видны сразу после подключения) и три «девопсовских» (N+1 в каталоге, медленный платёж в v2, 30% отказов склада).

- **Теги:** `block-2-start` (= `master`), `block-2-init` (сделан настоящим `init`), `block-3-instrumentation`, `block-4-agents` (свой Latency Agent + `observe.checks.ts`). После каждого релиза `next-observe` теги пересобираются.
- **Две «выкатки»:** `npm run observer` в одном терминале, `npm run dev:v1` / `npm run dev:v2` в другом — история телеметрии сохраняется между версиями, как при настоящем деплое.
- **Нагрузка:** `npm run load 40`. Для багов фронтенда она не нужна — их вызывает сам участник кликами; для проверок по расписанию тоже.
- **`npm run doctor`:** Node, зависимости, обзервер нужной версии, порт, теги, «блоки работают без Wi-Fi», настоящий AI.
- **Дома:** клонировать, `npm install`, `npm run doctor`. Конференционный Wi-Fi на это не рассчитываем.

## Исправления к исходному плану

1. **Детектор считает по корневым серверным спанам** (`SpanKind.SERVER`) или по каждой операции, а не по всем спанам. Next создаёт около 7 спанов на запрос, и 30% ошибок inventory размылись бы ниже порога 20%.
2. **`streamUI` не используем.** Он переехал в `@ai-sdk/rsc`, а документация AI SDK 7 пишет: «experimental, we recommend AI SDK UI».
3. **Один LLM-конвейер, карточки — из фактов:** модель пишет только текст выводов, а карточки строит код из результатов инструментов данных. Они уходят в чат событием `card` сразу после вызова инструмента. Второго вызова LLM нет (см. схему ниже; решение принято на шаге 14 журнала).
4. **Имя модели берём из env**, не хардкодим `gemini-2.0-flash`.
5. **Версии и имена:** Next 16, `next-observe`, `next-observe/debug`.
6. **Детектор:** фильтр по времени вместо `setTimeout` на каждый спан, без переменной с именем `window`.

### Схема: один LLM-конвейер, карточки из фактов

```
вопрос / детектор ──► ADK orchestrator (Gemini | Kitana | mock)
                        ├ latency_agent ─┐
                        ├ error_agent   ─┼─► инструменты данных (compare_versions, get_errors, get_trace, …)
                        └ traffic_agent ─┘            │ результат
                                                      ├──► модели (рассуждение → текст отчёта)
                                                      └──► cardsFromResult() → событие card   ← код, не модель
POST /api/chat → поток NDJSON: status → step… → card… → report
/chat: шаги вживую → карточки (регрессия, ошибки, N+1, горячая точка, нет трафика, трейсы) → отчёт
```

**Почему карточки строит код, а не Report Agent с `showAnomalyCard(...)`:**
- в карточке физически не может быть выдумки (кейс 2 — уверенная галлюцинация);
- у Kitana один вызов инструмента за ход: четыре карточки — это +4 хода по 5–10 секунд;
- работает и в `mock` (заглушка не заполнит обязательные поля карточки);
- урок для зала: **модель рассуждает — код показывает доказательства.**

## LLM: ADK + Gemini или Kitana (бюджет ≤ €20)

Все агенты — `LlmAgent` из `@google/adk`, другого LLM-кода в проекте нет. Модель выбирается одной функцией:

```ts
function getModel() {
  if (process.env.GEMINI_API_KEY) return process.env.GEMINI_MODEL   // встроенный Gemini в ADK
  return new KitanaLlm({ model: 'auto' })  // claude CLI → codex CLI → ollama → api-key
}
```

- Есть бесплатный ключ AI Studio → Gemini.
- Ключа нет → Kitana: подписка Claude / ChatGPT через CLI, Ollama или API-ключ.

### Флаг `OBSERVE_AI`: реальный AI или заглушка

У бесплатного Gemini из EU те же лимиты на запросы. Одно расследование — это оркестратор и 2–4 агента, каждый делает несколько ходов. При отладке лимит кончится быстро. Поэтому режим задаётся флагом:

| `OBSERVE_AI` | Что делает | Когда |
|---|---|---|
| `mock` (**по умолчанию в dev**) | `MockLlm extends BaseLlm`, сеть не трогает. Сценарий: вызвать инструменты агента с дефолтными аргументами → вернуть текст-сводку по их ответам. Report Agent вызывает `show*` с props из результатов | отладка детектора, инструментов, SSE и чата |
| `real` | `getModel()` → Gemini или Kitana | настоящая работа |
| `record` | `real` + запись каждого запроса и ответа в `.observe/llm-fixtures/` | подготовка демо |
| `replay` | ответы из записи, без сети; при промахе — `mock` | демо ведущего, если упадёт Wi-Fi |

```ts
function getModel(): BaseLlm | string {
  const real = () => process.env.GEMINI_API_KEY ? process.env.GEMINI_MODEL! : new KitanaLlm({ model: 'auto' })
  switch (process.env.OBSERVE_AI ?? 'mock') {
    case 'real':   return real()
    case 'record': return new RecordingLlm(real())
    case 'replay': return new ReplayLlm({ fallback: new MockLlm() })
    default:       return new MockLlm()
  }
}
```

- Ключ записи — агент + тип аномалии + номер хода, **а не хеш промпта**. В промпте есть traceId и время, хеш не совпадёт при следующем прогоне.
- В режиме `real` нужна очередь с минимальным интервалом между запросами и retry на 429: 4 агента параллельно быстро упрутся в лимит free tier. Плюс cooldown детектора, который уже есть.
- Для воркшопа: в блоке 4 участники сначала гоняют своего агента на `mock` (проверяют инструменты), потом переключают на `real`. Токены тратятся только на осмысленные прогоны.
- В UI чата бейдж `MOCK` / `REPLAY`, чтобы заглушку не приняли за ответ модели.

**Бюджет:**
- Запасной вариант за счёт ведущего: OpenRouter, €20, ключи с лимитом ~€0.5–1 на ключ.
- Живое демо: подписка Claude через CLI или платный ключ + replay на случай, если упадёт Wi-Fi.
- Оценка: ~20 чел × ~10 расследований × ~30k токенов ≈ 6M токенов → единицы € на дешёвых моделях.

**Проверить до воркшопа:**
- [ ] `@kitana-sdk/adk` с `@google/adk` 2.1.0 (последняя). Kitana тестировалась на ADK 1.6.
- [x] Gemini free tier доступен из EU (лимиты те же)
- [ ] Tool calling с 4 агентами + оркестратором на каждом провайдере цепочки.
- [ ] Kitana буферизует запросы с инструментами в одно событие. Для чата это нормально: события UI отправляются при выполнении инструмента, а не из токенов.
