# План воркшопа — AI-Native Observability

**Тема:** Building Self-Debugging Next.js Applications with OpenTelemetry
**Дата:** 10 ноября 2026, Португалия. **Длительность:** 3 ч 30 мин, смешанная аудитория.
**Формат:** гибрид. Участники работают только локально; прод (Vercel + дроплет) — демо ведущего, поднимается заранее.

**Слова** (как в README пакетов): **APM-агент** — `next-observe`, библиотека внутри приложения, только OpenTelemetry; **AI-агенты** — ADK-агенты внутри обзервера; **обзервер** — `next-observer` целиком (сервер, UI, детектор, проверки по расписанию, AI-агенты), запускается через `npx`. Просто «агент» не говорим — зал путает.

**Приложение:** Porto Shop (`workshop-ai-observability`), Next 16, шесть багов фронтенда и три «девопсовских». Дома: `npm install` и `npm run doctor` — после «All set» всё работает без Wi-Fi. Теги блоков пересобираются под новый порядок — см. «Подготовка».

---

## Главная идея порядка

Переписано 17 октября 2026. Сначала участники разбирают каждую часть телеметрии **по отдельности и руками**: что такое спан, как он едет по OTLP, как его получить, как добавить свой, как найти по сырым данным настоящий баг. **Только потом** появляется обзервер — как инструмент, который показывает то же самое за секунды и даёт работать с AI-агентами.

Почему так:
- знание остаётся с участником и работает в любом бэкенде (Grafana, Datadog, Honeycomb, Dynatrace): **данные и то, куда они уходят, — разные вещи**;
- обзервер перестаёт быть магией: участник уже сам сделал всё, что он автоматизирует;
- понятны границы: почему автоинструментация не видит причину 400 и почему инцидент F не поймать без своего атрибута.

Риск — поздний первый результат и усталость от абстракций. Поэтому «для чего» звучит в первые 5 минут через собственный опыт (кликают по магазину и не видят багов), а каждое понятие теории сразу становится JSON на экране участника.

## Блоки подробно

### 0. Пролог: станция слепа (10 мин) — картинки 01, 02, 03, 07

*"In space, no one can hear your users scream."* Знакомим с Kevin (01) и экипажем (02), станция Porto-7 (03). Lord Manager: колония Sandy-9 перестала заказывать. У Kevin всё зелёное (07) — ошибка была в терминале колонистов, на их планете.

1. *3 мин.* `npm run doctor` у всех.
2. *5 мин.* Голый магазин (без телеметрии). Все просто пользуются: товар 1 — «Save for later», количество 20 — Buy; товар 2; товар 4 — «Show details»; поиск на главной. В DevTools не смотрим.
3. *2 мин.* Вопрос залу: «сколько багов вы заметили?» Обычно один-два. «Их шесть. Два из них вы не увидите никогда — они в чужом браузере. Как бы вы узнали?» Это и есть «для чего».

### 1. Теория (20 мин) — картинка 05

Kevin на болотной планете у Master O'Tel. *"Logs you have. Story you have not."* · *"Grep leads to anger. Anger leads to more grep."*

- Спан — «что происходило, сколько, с какими атрибутами»; дерево спанов во времени — трейс. Не замена логов: логи — каждый пишет в свой блокнот, трейс — один журнал на весь рейс.
- Атрибуты, события (исключение — событие на спане), статус.
- Ресурс: `service.name`, `service.version` — без версии на каждом спане не ответить «какая выкатка сломала».
- Контекст: `traceparent` связывает браузер, сервер и соседние сервисы в один трейс.
- Сигналы: трейсы, метрики, логи — сегодня работаем с трейсами.
- OTel = API + SDK + протокол OTLP + семантические соглашения (`http.route`, `http.status_code`).
- Ключевой тезис: **данные и то, куда они уходят, — разные вещи.** Grafana (Tempo), Dynatrace, Honeycomb, Datadog слушают тот же OTLP.
- Два слова про слова: APM-агент (в приложении) и AI-агенты (в обзервере) — разные вещи.

Каждое понятие — с соответствием из истории (таблица выше) и сразу обещание: «через 10 минут вы увидите это в JSON».

### 2. Транспорт OTLP (20 мин, руками) — картинки 06, 07b

TR-4CE вручает Kevin «чёрный ящик» OTLP (06): *"Sadly, only one of them matters."*

1. *7 мин.* **Свой приёмник.** `tools/receiver.mjs` в магазине — каркас HTTP-сервера на порту 4318 (стандартный порт OTLP/HTTP), принимает `POST /v1/traces`, отвечает `200 {}` и дописывает каждую пачку в `.telemetry/spans.ndjson`. Дырка для участника: пройти `resourceSpans → scopeSpans → spans` и напечатать сервис, имя, длительность, статус. `npm run receiver`.
2. *5 мин.* **Спан руками.** `curl -X POST localhost:4318/v1/traces -H 'content-type: application/json' -d @tools/span.json`. Первый JSON в своём терминале — картинка 07b, Kevin плачет от счастья. Правят `span.json`: другое имя, атрибут, статус ошибки — видят результат.
3. *8 мин.* **Что внутри и как едет.**
   - `traceId`, `spanId`, `parentSpanId`; время в наносекундах; ресурс отдельно от спанов.
   - Два спана с общим `traceId` и родителем — дерево. Тот же `traceId` «из другого сервиса» — так работает `traceparent`.
   - JSON или protobuf, gzip; пачки (почему спаны приходят с задержкой); что будет, если приёмник лёг: экспортёр теряет спаны, приложение не ломается.

### 3. Инструментация (25 мин, руками) — картинка 08

Датчики корпуса докладывают: *"Voyage took 20 minutes. Status: OK-ish."* B3-EP пищит «400». *"It's a trap!"*

1. *10 мин.* **APM-агент в магазин — руками, три файла:** `npm i next-observe`, `instrumentation.ts` (`register()`), `instrumentation-client.ts`, `withObserve()` в `next.config`. Адрес не настраиваем: `next-observe` по умолчанию шлёт OTLP/JSON на `127.0.0.1:4318` — в их приёмник. Снова кликают по магазину и видят в терминале:
   - автоматические спаны: HTTP-сервер, fetch, загрузка страницы в браузере;
   - **ошибки из браузера** — те самые баги из блока 0, теперь в JSON;
   - чего автоматика не даёт: `POST /api/checkout` → 400, но почему — нет.
2. *10 мин.* **Свой спан** `placeOrder` с атрибутами; причина 400 — атрибутом на спане (`quantity 20 > limit 10`, картинка 08). Принцип: причину надо положить в спан.
3. *5 мин.* **`'use observe'`** в начале файла в `lib/` — функции становятся спанами с `code.filepath`, без ручных обёрток.

Отставший: тег `block-3-instrumentation`.

### 5. Обзервер: отображение и работа с AI (40 мин, руками) — картинки 14–17

1. *5 мин.* **ИИ станции просыпается** (14): *"Good evening, Kevin."* Останавливаем свой приёмник, запускаем `npm run observe` (`next-observer dev`) — **на том же порту 4318**. В приложении не меняется ни строчки: тот же OTLP. *"Where were you four hours ago?" — "Nobody connected me, Kevin."* Упомянуть: `npx next-observer init` делает три файла из блока 3 за вас.
2. *10 мин.* **Те же кейсы за секунды** — каждый со ссылкой «в блоке 4 это был скрипт N»:
   - Errors — четыре бага браузера и 400 (кейсы 1–2);
   - Overview — `GET /api/products` 65% (кейс 3);
   - waterfall трейса каталога — 5 одинаковых `getProductById` (кейс 4);
   - баннер регрессии и страница операции v1 vs v2 (кейс 5);
   - чинят один-два бага: «Copy prompt» с карточки → Claude Code / Codex (`null.push`, 204 → `[]`, цикл запросов).
3. *5 мин.* **Ночной патруль** (16): `observe.checks.ts`, магазин v2 **без нагрузки** — проверка «checkout takes under a second» краснеет сама, в чате аномалия. «Кто из ваших пользователей сообщил бы об этом в три часа ночи?»
4. *15 мин.* **AI-агенты** (15): детектор → расследование в чате само; свой Latency Agent в `observe.agents.ts` (20 строк), сначала `OBSERVE_AI=mock`, потом `real`. Карточки доказательств строит код, не модель. Бюджет (17): `OBSERVE_AUTO_INVESTIGATIONS`, по умолчанию 5 в час — *"I'm afraid I can't investigate that."*
5. *5 мин.* **Что узнали про AI-агентов** — кейсы 1–4 ниже коротко: инструмент важнее промпта, уверенная галлюцинация, язык адаптера, «не заглянул внутрь».

Отставший: тег `block-5-observer`.

### 6. Инцидент F + прод (20 мин, ведущий) — картинка 18

Тег `block-6-incident-f` — блок 5 плюс «выкатка» v3. Телепорт путает капсулы, таможенный дроид сверяет манифест: *"These aren't the goods you ordered."*

1. Обзервер запущен, магазин — `npm run dev:v2`, нагрузка `npm run load 40`: в чате аномалия про медленный checkout. «Чиним»: останавливаем v2, `npm run dev:v3`, снова нагрузка.
2. Overview: ошибок нет (кроме привычного склада), checkout снова быстрый. «Починили?»
3. Вопрос залу: «как это заметить руками?» **Не обещаем показать в браузере**: за 40 открытий `/product/1` под обычной нагрузкой чужой товар не пришёл ни разу, под `RPS=30` — 2 раза из 40. Как в настоящем инциденте: «иногда», и поэтому двое суток искали не там.
4. В чате — «Wrong data · 3 responses came back wrong»: asked for "1", got back "3". С настоящей моделью — карточка «v2 — 0 of 31, v3 — 11 of 191 answers were not the ones asked for» и вывод «v3 is where wrong data begins». Трейс: плашка «Wrong data», метка на спане `getProductById`, событие `integrity_check` (expected / actual).
5. Код: `lib/pool.ts` (30 строк — пулер в transaction-режиме отдаёт ответы не по порядку) и одна строка в `lib/db.ts`, где приложение само спрашивает «я получил то, что просил?».
6. Вывод: автоинструментация этого не видит и не может — приложение должно решить, что это стоит измерить. История двух суток и шести «починок» — из `APM_FINDINGS.md`.
7. *5 мин.* Прод: тот же магазин на Vercel, обзервер на дроплете — по [PROD_DEMO.md](PROD_DEMO.md).

Проверка «product 1 is the mug» в `observe.checks.ts` за короткий прогон не падает: одиночный запрос снаружи почти никогда не попадает в путаницу. Это тоже говорим вслух — внешняя проба ловит такое только случайно.

### 7. Эпилог и Q&A (10 мин) — картинка 19

Lord Manager: *"Impressive. Most impressive."* Kevin повышен до бессменного дежурного. На экране — **DON'T PANIC**.

- Ваш AI-агент — файл на 20 строк, ваши проверки — файл на 10.
- Всё, что вы сделали в блоках 2–4, работает с любым бэкендом: тот же OTLP можно отправить в Grafana или Datadog.

**Слайд из практики.** AI-ревью в pre-commit нашло пять из шести багов фронтенда и заблокировало коммит; расхождение гидратации — не нашло: оно видно только при исполнении. Ревью кода и наблюдаемость ловят разное.

## Лесенка: от «не работает кнопка» до «упал прод»

Порядок — от того, что знакомо любому фронтендеру, к тому, что обычно видит только эксплуатация. Каждый баг участник сначала находит руками по сырым данным (блок 4), потом — в обзервере (блок 5).

| Уровень | Что ломается | Где в магазине | Что видит пользователь | Руками, блок 4 | В обзервере, блок 5 |
|---|---|---|---|---|---|
| 1. JavaScript | исключение в обработчике клика | «♡ Save for later» | кнопка не работает | кейс 1: `exception` на спане браузера | Errors: `uncaught error`, Cannot read properties of null (reading 'push') |
| 1 | ошибка рендера, пойманная `error.tsx` | «Show details», товар 4 | «Something went wrong» | кейс 1 | Errors: `console.error`, «occurred in the `<Details>` component» |
| 1 | расхождение гидратации | «N people are looking» | ничего | кейс 1 | Errors: `hydration mismatch` — `<Viewers>` → `<p>`, `+ 30 / − 5` |
| 1 | ответ не JSON | отзывы, товар 2 (API отвечает 204) | вечное «Loading reviews…» | кейс 1 | Errors: `invalid JSON response`; сервер «здоров» |
| 2. API | фронт и бэк расходятся в правилах | количество 20 при лимите 10 | «Payment failed» без причины | кейс 2 (причина — из своего спана) | Errors: `POST /api/checkout` — HTTP 400 |
| 3. Состояние | эффект → `setState` → эффект | поиск в каталоге | ничего, поиск «работает» | кейс 3 | Overview: `GET /api/products` — 65% всех запросов |
| 4. Структура | N+1 | каталог (`lib/catalog.ts`) | «чуть медленно» | кейс 4 | waterfall: 5 одинаковых `getProductById` |
| 5. Деплой | регрессия в v2 | платёж (`lib/payment.ts`) | оплата 2 секунды вместо 0.2 | кейс 5 | баннер регрессии, страница операции, Latency Agent |

## Кейсы для блока агентов (реальные, воспроизводимые)

Взяты из проверки ADK + Kitana (журнал, шаг 10). Скрипты лежат в `spikes/adk-kitana/`. Каждый кейс — это «сломали → увидели → исправили → поняли принцип». В блоке 5 — коротко, за ~5 минут; желающие повторяют дома.

### Кейс 1. «Агент сдался» — проектирование инструмента важнее промпта

- **Вопрос:** «Checkout is slow. Which operation and which deployment caused it?»
- **Что произошло:** агент вызвал `get_operation_stats({ operation: "checkout" })`. Операции с таким именем нет, есть `chargePayment`. Инструмент вернул `[]`, и агент ответил «данных нет».
- **Исправление в инструменте, а не в промпте:** при пустом совпадении возвращать все операции с пометкой `note: "no operation matches …, showing all"`. После этого 2 из 2: агент сам связал checkout → `chargePayment`, нашёл `v2`, привёл точные p50/p95/p99.
- **Принцип:** пользователь говорит на языке бизнеса, спаны — на языке кода. Инструмент должен помогать модели сопоставить их, а не ставить ей подножку пустым ответом.

```bash
npm run agent   # в spike.mjs можно вернуть фильтр без fallback и увидеть провал
```

### Кейс 2. «Уверенная галлюцинация» — оркестратор на неполных данных

- **Вопрос:** «Users say checkout is slow and product pages sometimes fail. What is going on?»
- **Что произошло (1 прогон из 3):** оркестратор вызвал обоих специалистов, но специалист по латентности не выполнил свой инструмент. Оркестратор всё равно написал уверенный отчёт: «checkout медленный, *скорее всего*, из-за того же inventory». Этого в данных нет, это две независимые проблемы.
- **В удачных прогонах (2 из 3):** обе проблемы названы **независимыми**, с точными цифрами и текстом исключения.
- **Принципы:**
  - отчёт — только из фактов, которые вернули инструменты. Если данных нет, так и сказать, без догадок;
  - LLM недетерминирована: один прогон ничего не доказывает. Нужны **evals** — автоматические проверки ответа, как в наших скриптах (PASS/FAIL по фактам);
  - это аргумент в пользу DSL и структурированного вывода (карточки с полями) вместо свободного текста.

```bash
npm run orchestrator   # запустить 3–5 раз и сравнить отчёты
```

### Кейс 3. «Агент заговорил по-русски» — промпт адаптера протекает в ответ

- **Что произошло:** при английском вопросе и английской инструкции один из ответов пришёл на русском.
- **Первая гипотеза (неверная):** «Kitana запускает личный `claude` CLI участника, и его настройки протекают в агента».
- **Настоящая причина — в коде адаптера.** `@kitana-sdk/adk` описывает модели инструменты и пересказывает историю вызовов **по-русски**: «Доступные инструменты (JSON Schema)…», «Если нужно вызвать инструмент, ответь ТОЛЬКО валидным JSON…», «Вызов инструмента …», «Результат вызова …». Модель подхватывает язык контекста.
- **Исправление:** промпт адаптера на английском или нейтральный по языку; до этого — явное `Answer in English` в инструкции каждого агента.
- **Принципы:**
  - агент — это модель плюс **всё**, что попадает ей в контекст: инструкция, системный промпт адаптера, пересказ истории;
  - первую правдоподобную гипотезу надо проверять: мы нашли причину, только прочитав код адаптера;
  - провайдер-адаптер — часть поведения агента, и его надо тестировать так же, как свой код.

### Кейс 4. «Агент не заглянул внутрь» — N+1 видно только в трейсе

- **Вопрос:** «The product catalog is slower than expected but no single span stands out. What is wrong?»
- **Удачно (4 из 5):** `search_traces` → `get_trace` → `repeated: count=5, totalMs=90` → «N+1 confirmed: 5 identical db.query calls… should be batched».
- **Неудачно (1 из 5):** специалист ограничился статистикой (p50 = p95 = p99 = 120 мс, регрессии нет) и не открыл ни одного трейса. Вывод: «узкого места не нашли».
- **Принципы:**
  - агрегаты не показывают **структуру**: N+1 виден только внутри трейса. Инструмент, который сам находит повторы (`repeated`), превращает поиск иголки в одно поле ответа;
  - в инструкции специалиста надо явно просить «открой пример трейса»;
  - один и тот же вопрос даёт разные траектории, поэтому evals гоняют много раз.

```bash
OBSERVE_AI=real npx vitest run e2e/investigate.real.test.ts --silent=false   # протокол каждого шага
```

### Цифры, которые стоит показать

| | Время ответа |
|---|---|
| Один агент с инструментом | ~10s |
| Оркестратор + 2 специалиста | ~35–45s |
| Оркестратор + 3 специалиста (next-observe/agents) | ~33–52s |

## Исправления к исходному плану

1. **Детектор считает по корневым серверным спанам** (`SpanKind.SERVER`) или по каждой операции, а не по всем спанам. Next создаёт около 7 спанов на запрос, и 30% ошибок inventory размылись бы ниже порога 20%.
2. **`streamUI` не используем.** Он переехал в `@ai-sdk/rsc`, а документация AI SDK 7 пишет: «experimental, we recommend AI SDK UI».
3. **Один LLM-конвейер, карточки — из фактов:** модель пишет только текст выводов, а карточки строит код из результатов инструментов данных. Они уходят в чат событием `card` сразу после вызова инструмента. Второго вызова LLM нет (см. схему ниже; решение принято на шаге 14 журнала).
4. **Имя модели берём из env**, не хардкодим `gemini-2.0-flash`.
5. **Версии и имена:** Next 16, `next-observe`, `next-observe/debug`.
6. **Детектор:** фильтр по времени вместо `setTimeout` на каждый спан, без переменной с именем `window`.

### Схема: один LLM-конвейер, карточки из фактов

```
вопрос / детектор ──► ADK orchestrator (Gemini | Kitana | mock)
                        ├ latency_agent ─┐
                        ├ error_agent   ─┼─► инструменты данных (compare_versions, get_errors, get_trace, …)
                        └ traffic_agent ─┘            │ результат
                                                      ├──► модели (рассуждение → текст отчёта)
                                                      └──► cardsFromResult() → событие card   ← код, не модель
POST /api/chat → поток NDJSON: status → step… → card… → report
/chat: шаги вживую → карточки (регрессия, ошибки, N+1, горячая точка, нет трафика, трейсы) → отчёт
```

**Почему карточки строит код, а не Report Agent с `showAnomalyCard(...)`:**
- в карточке физически не может быть выдумки (кейс 2 — уверенная галлюцинация);
- у Kitana один вызов инструмента за ход: четыре карточки — это +4 хода по 5–10 секунд;
- работает и в `mock` (заглушка не заполнит обязательные поля карточки);
- урок для зала: **модель рассуждает — код показывает доказательства.**

## LLM: ADK + Gemini или Kitana (бюджет ≤ €20)

Все агенты — `LlmAgent` из `@google/adk`, другого LLM-кода в проекте нет. Модель выбирается одной функцией:

```ts
function getModel() {
  if (process.env.GEMINI_API_KEY) return process.env.GEMINI_MODEL   // встроенный Gemini в ADK
  return new KitanaLlm({ model: 'auto' })  // claude CLI → codex CLI → ollama → api-key
}
```

- Есть бесплатный ключ AI Studio → Gemini.
- Ключа нет → Kitana: подписка Claude / ChatGPT через CLI, Ollama или API-ключ.

### Флаг `OBSERVE_AI`: реальный AI или заглушка

У бесплатного Gemini из EU те же лимиты на запросы. Одно расследование — это оркестратор и 2–4 агента, каждый делает несколько ходов. При отладке лимит кончится быстро. Поэтому режим задаётся флагом:

| `OBSERVE_AI` | Что делает | Когда |
|---|---|---|
| `mock` (**по умолчанию в dev**) | `MockLlm extends BaseLlm`, сеть не трогает. Сценарий: вызвать инструменты агента с дефолтными аргументами → вернуть текст-сводку по их ответам. Report Agent вызывает `show*` с props из результатов | отладка детектора, инструментов, SSE и чата |
| `real` | `getModel()` → Gemini или Kitana | настоящая работа |
| `record` | `real` + запись каждого запроса и ответа в `.observe/llm-fixtures/` | подготовка демо |
| `replay` | ответы из записи, без сети; при промахе — `mock` | демо ведущего, если упадёт Wi-Fi |

```ts
function getModel(): BaseLlm | string {
  const real = () => process.env.GEMINI_API_KEY ? process.env.GEMINI_MODEL! : new KitanaLlm({ model: 'auto' })
  switch (process.env.OBSERVE_AI ?? 'mock') {
    case 'real':   return real()
    case 'record': return new RecordingLlm(real())
    case 'replay': return new ReplayLlm({ fallback: new MockLlm() })
    default:       return new MockLlm()
  }
}
```

- Ключ записи — агент + тип аномалии + номер хода, **а не хеш промпта**. В промпте есть traceId и время, хеш не совпадёт при следующем прогоне.
- В режиме `real` нужна очередь с минимальным интервалом между запросами и retry на 429: 4 агента параллельно быстро упрутся в лимит free tier. Плюс cooldown детектора, который уже есть.
- Для воркшопа: в блоке 5 участники сначала гоняют своего агента на `mock` (проверяют инструменты), потом переключают на `real`. Токены тратятся только на осмысленные прогоны.
- В UI чата бейдж `MOCK` / `REPLAY`, чтобы заглушку не приняли за ответ модели.

**Бюджет:**
- Запасной вариант за счёт ведущего: OpenRouter, €20, ключи с лимитом ~€0.5–1 на ключ.
- Живое демо: подписка Claude через CLI или платный ключ + replay на случай, если упадёт Wi-Fi.
- Оценка: ~20 чел × ~10 расследований × ~30k токенов ≈ 6M токенов → единицы € на дешёвых моделях.

**Проверить до воркшопа:**
- [ ] `@kitana-sdk/adk` с `@google/adk` 2.1.0 (последняя). Kitana тестировалась на ADK 1.6.
- [x] Gemini free tier доступен из EU (лимиты те же)
- [ ] Tool calling с 4 агентами + оркестратором на каждом провайдере цепочки.
- [ ] Kitana буферизует запросы с инструментами в одно событие. Для чата это нормально: события UI отправляются при выполнении инструмента, а не из токенов.
