## Несколько проектов и корреляция инцидентов

Добавлено 15 октября 2026 по просьбе автора. **Статус: запланировано, не начато.** Порядок относительно шагов 79–80 и AI-агентов как команды — решить с автором.

### 1. Смотреть больше одного проекта

Что уже есть: хранилище и API различают сервисы по `service.name` (`GET /api/services`, фильтр `service` в запросах), детектор ведёт окна по паре «сервис + операция». Чего нет:

- **Проект как понятие в UI:** переключатель проекта в шапке (или «все»), дашборд, трейсы, ошибки, Checks и чат — в рамках выбранного. Сейчас несколько сервисов смешиваются на общих страницах.
- **Детектор по проектам:** правила уровня приложения (общая доля ошибок, «тишина» `no_traffic`) и их пауза сейчас общие на весь обзервер — аномалия проекта A заглушит такую же у проекта B на 5 минут, а молчание одного проекта не видно, пока шлёт другой. Считать их по каждому сервису.
  - **Решение (15 октября):** причина — ключ состояния детектора без проекта, а не отсутствие очереди. Исправление — добавить `service.name` в ключ окна и паузы, как уже сделано для правил по операциям. Движок очередей (BullMQ) не берём: ему нужен Redis, а обзервер ставится одним `npx` без зависимостей; обзервер — один процесс, и расследования не должны переживать перезапуск (через час они бесполезны, поэтому в шаге 78 бюджет, а не длинная очередь). Вернуться, только если обзервер станет общим сервисом на несколько процессов или машин — и тогда сначала очередь в таблице SQLite (она уже в плане), Redis — только если упрёмся в одну машину.
- **Бюджет расследований (шаг 78):** сейчас один на обзервер. Решить: общий потолок (он защищает подписку) плюс доля на проект, чтобы шумный проект не съел расследования остальных.
- **Настройки проекта:** `observe.checks.ts` и `observe.agents.ts` сейчас читаются из одной папки `--root`. Нужно несколько источников (по папке на проект, или проект присылает свои настройки), и свой `OBSERVE_APP_URL` для проверок каждого.
- **Ключи приёма:** на общем обзервере — свой `x-api-key` на проект, чтобы проект не мог писать под чужим именем.
- AI-агенты получают проект в вопросе и по умолчанию ищут в нём, но могут смотреть соседей (нужно для пункта 2).

### 2. Корреляция инцидентов

Чтобы одна причина, видная в нескольких местах, разбиралась одним расследованием, а не пятью.

- **Группа инцидентов:** аномалии, близкие по времени (окно — несколько минут), объединяются, если у них есть общее: один проект и версия (выкладка), общий нижестоящий сервис или внешний адрес в трейсах (`peer`, URL исходящих запросов, имя БД), одинаковое сообщение ошибки. Начать с правил, без модели.
- **Связь между проектами по трейсам:** если проект A вызывает B (общий `traceId` через `traceparent`), ошибка B — вероятная причина ошибок A. Граф «кто кого вызывает» строится из спанов.
- **Одно расследование на группу:** первое расследование получает остальные аномалии группы как контекст; новые аномалии той же группы добавляются к нему (`noted` со ссылкой на группу), а не тратят бюджет.
- **Выкладка как событие:** новая `service.version` в одном из проектов — отметка на шкале времени; аномалии сразу после неё связываются с ней.
- **В UI:** группа в списке расследований (одна строка, внутри — аномалии по проектам) и общая шкала времени по проектам.
- **Инструмент для AI-агентов:** `get_related_incidents` — что ещё случилось рядом по времени и по графу вызовов; факты только из кода, как и карточки.
- Учебный сценарий для воркшопа (если войдёт): магазин + отдельный сервис склада, падение склада даёт ошибки в магазине — одна группа, причина в складе.

## Где что хранить

Граница: что пишет человек — в файлы; что пишет обзервер — в базу.

| Что | Где | Почему |
|---|---|---|
| Настройки агентов, привязка к типам, лимиты | файлы в репозитории приложения (`observe.agents.ts`, `observe.checks.ts`) | видно в диффе, ревью в PR, одинаково у команды |
| Знания агентов | markdown-файлы в репозитории | то же |
| История чата, память агентов, счётчик токенов, аномалии, результаты проверок | SQLite, один файл (`.observe/observer.db`, в `.gitignore`) | пишет обзервер, часто и параллельно; нужны запросы («токены агента за неделю») |
| Трейсы (спаны) | пока в памяти, как сейчас | на порядки больше остального; хранилище уже за интерфейсом `StorageAdapter`, переедет отдельно |

- SQLite — потому что ничего не надо ставить (`npx`, воркшоп, дроплет). Проверить статус встроенного `node:sqlite` в нашей версии Node (22.18+); нативных зависимостей избегать — ломаются при установке на чужих машинах.
- Правки из интерфейса (когда появятся) писать обратно в файлы репозитория, а не в базу.
- База нужна не сразу: шаги 78–80 работают в памяти. Она появляется на пункте 5; тогда же в неё переезжает история чата, и счётчик токенов перестаёт обнуляться при рестарте.

## Расширение пакета: APM-инструментор для Go

Добавлено 12 октября 2026 по просьбе автора. **Статус: запланировано, реализация и выкладка не начаты.** Это отдельное расширение продукта; шаги 78–80 и программа воркшопа выше остаются в прежнем порядке. Сначала локальная проверка, затем Kitana локально; облачный обзервер с Claude API-ключом — после неё.

### Решение: явная инструментация поверх OpenTelemetry

Для первого варианта вмешательство в бинарник не требуется. Обычный Go компилируется в машинный код, поэтому подход с JS-loader/подменой функций в runtime сюда напрямую не переносится. Нужен отдельный Go-модуль — тонкий APM-инструментор поверх официальных OTel API/SDK и OTLP/HTTP exporter. Он отправляет трейсы в существующий `next-observer`; AI-зависимостей внутри Go-сервиса нет. Имя и module path выбрать перед реализацией, пока не объявлять пакет опубликованным.

Предлагаемый API (это проект интерфейса, ещё не существующий код):

```go
err := observe.Run(ctx, "prices.refresh", func(ctx context.Context) error {
    return refreshPrices(ctx)
})
```

- `Run` создаёт span выбранной операции, передаёт производный `context.Context`, завершает span и возвращает исходную ошибку. Запись ошибки включает `RecordError` и статус `Error`, а не только событие исключения.
- Для произвольных сигнатур — `ctx, span := observe.Start(ctx, name)` и `defer span.End()` внутри функции; ошибку отмечают явно. Одна универсальная обёртка не может сохранить все возможные Go-сигнатуры автоматически.
- Panic записывается с ограниченными диагностическими данными и передаётся дальше; не превращать его в обычную ошибку и не менять контракт вызывающего кода. Сохранение поведения проверять отдельно.
- Контекст связывает вложенные функции, SQL и HTTP с одной задачей. В новые goroutine его нужно передавать явно; не обещать автоматического переноса контекста во все goroutine.
- Такие spans измеряют **время выполнения по часам**, включая ожидания I/O, статус и ошибки. CPU-время конкретной функции и allocations требуют отдельного профилирования (`pprof`/runtime), обёртка их сама не измеряет.

### Первый объём

1. Инициализация/остановка exporter: имя сервиса, revision, instance, endpoint, ingest key; корректный совместный lifecycle с уже настроенным OTel provider, без второго дублирующего exporter.
2. Выборочные функции и фоновые задачи: `Start`/`Run`, длительность, ошибка, panic, вложенные spans и стабильное имя операции. Измерять выбранные функции, не весь процесс по умолчанию.
3. HTTP: middleware для входящих запросов и обёртка `http.RoundTripper` для исходящих; endpoint/resource, HTTP status, задержка, попытка повтора, безопасные метаданные Cloudflare. Чтение тела и декодирование выделять отдельным span — время до заголовков не равно времени полной загрузки.
4. PostgreSQL/pgx: tracing hooks и отдельный span жизненного цикла запроса/чтения результата; имя запроса, длительность, SQLSTATE, этап ожидания пула. Конкретный pgx tracer и границы измерений проверить на используемой версии; полный SQL, параметры и DSN по умолчанию не экспортировать.
5. Cron: root span запуска (`job`, `run_id`, revision), дочерние этапы fetch/write/summary и агрегаты updated/unchanged/skipped/failed. Фоновую задачу обозначать корректным span kind, не маскировать её под HTTP-запрос ради детектора.
6. Экспорт пакетами через ограниченную очередь с коротким timeout. Недоступность обзервера не блокирует рабочую функцию, не меняет её результат и не создаёт повторных SQL/API-вызовов. Потери при перегрузке показывать счётчиком; безусловную доставку при ограниченном буфере не обещать.

### Расследование редких cron-инцидентов

Один сбой часовой задачи должен запускать разбор независимо от web-порога `minSamples=5`. Нужен отдельный сигнал ошибки фоновой задачи / правило детектора и дедупликация по задаче, этапу, коду ошибки и revision; использовать бюджет из шага 78. Нельзя просто снизить глобальный порог: обычные долгие cron-запуски начнут давать ложные расследования задержек.

Две первые локальные фикстуры — реальные случаи predictionmarkets:

- `catalog-statistics` → `soccer:competitions`: SQLSTATE `57014`, лимит 5000 ms, старый snapshot сохранён; показать отличие от последующих успешных запусков.
- `prices-all` → Gamma markets: HTTP `403`, page 453, visited 45200, Cloudflare/HTML и cf-ray; частичные обновления сохранены. Разбор не должен выдавать неизвестную причину WAF/origin-отказа за установленный факт.

### Проверки и порядок

- [ ] Локальный Go-сервис → OTLP → существующий обзервер: функции и вложенные spans видны в waterfall.
- [ ] Длительность, ошибки, panic и отмена; исходные результаты/ошибки сохраняются, goroutine не теряют явно переданный контекст.
- [ ] HTTP: задержка заголовков, задержка тела, 403 и таймаут; pgx: ожидание пула, выполнение/чтение и statement timeout — на локальных фикстурах.
- [ ] Обзервер недоступен / очередь переполнена: бизнес-вызовы продолжаются, число потерь измеряется, память ограничена.
- [ ] Один cron-сбой создаёт одно расследование, соблюдаются cooldown и общий бюджет, нормальный долгий cron не считается регрессией сам по себе.
- [ ] Benchmark с включённой и выключенной инструментацией: накладные расходы CPU/RAM/latency; mutation check и интеграционный прогон Go → collector на опубликованных/упакованных артефактах.
- [ ] После этого локальная проверка реального AI через Kitana; облако с Claude API-ключом отдельно, без автоматического изменения production cron.

Позже, только при подтверждённой необходимости: генерация вставок в исходный код по Go AST и явным аннотациям, чтобы уменьшить ручную работу. eBPF/zero-code instrumentation и перехват скомпилированных функций — отдельное исследование совместимости/накладных расходов, не зависимость первого выпуска. Явная обёртка не перехватит все прямые вызовы функции, которую мы не изменили: для неё нужно изменить функцию, место вызова или сборку.

Источники: [Go instrumentation](https://opentelemetry.io/docs/languages/go/instrumentation/), [как работает Go zero-code instrumentation](https://github.com/open-telemetry/opentelemetry-go-instrumentation/blob/main/docs/how-it-works.md).
